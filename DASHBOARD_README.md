# EOSC Pilot Node Dashboard

A browser-based monitoring dashboard for EOSC Beyond Pilot Nodes. It reads JSON
reports generated by four Java data-collection checks and presents capability,
catalogue, uptime, and Federated Search visibility data across all registered
nodes. Reports can also be triggered directly from the UI — one check at a
time, or all of them for every node in one go via **Check All**.

---

## File Naming Conventions

| File | Description |
| ---------------------------------- | -------------------------------------------------------------------- |
| `node_registry_summary.json`       | Central registry — fixed name, always at the `data/` root            |
| `endpoint_report.json`             | Endpoint capability report (generated by `CheckNodeCapabilities`)    |
| `catalogue_services_report.json`   | Exchange Services report (generated by `CheckCatalogueServices`)     |
| `argo_uptime_report.json`          | ARGO uptime report (generated by `CheckServiceUptime`)               |
| `front_office_metrics_report.json` | Federated Search report (generated by `CheckOtherMetrics`)           |

Node folder names must exactly match the `node_name` field in `node_registry_summary.json`.

---

## Architecture

```text
data/
├── node_registry_summary.json        ← registry of all nodes
├── CESSDA/
│   ├── endpoint_report.json
│   ├── catalogue_services_report.json
│   ├── argo_uptime_report.json
│   └── front_office_metrics_report.json
├── CLARIN/
│   └── ...
└── ...
```

The Spring Boot backend serves the dashboard files and exposes a REST API at
 `/api/`. The dashboard HTML files make JSON fetches relative to that path and
 require an HTTP server — opening them directly via `file://` will not work
 because browsers block local file fetches.

## Data Collection Checks

Four Java classes generate the report files, plus a `CheckAll` job that runs
all of them together. Each can be run from the command line or triggered via
the dashboard UI; none requires end-user credentials any more (see each
check below).

### CheckNodeCapabilities

Queries the EOSC Node Registry and writes `node_registry_summary.json` and
per-node `endpoint_report.json` files. Requires a node API key configured
in `application.properties`.

```text
CheckNodeCapabilities
```

Triggered via: `POST /api/run/node-capabilities`

### CheckCatalogueServices (Exchange Services)

Queries a node's Resource Catalogue API, checks the availability of each listed
service's webpage, and writes `catalogue_services_report.json`.

```text
CheckCatalogueServices NODE_NAME [api_base_url] [quantity] [dashboard_dir]
```

| Argument        | Required | Default                             | Description |
| --------------- | -------- | ----------------------------------- | ----------- |
| `NODE_NAME`     | Yes      | —                                   | Node name; must match `node_registry_summary.json` |
| `api_base_url`  | No       | CESSDA staging URL                  | The node's Resource Catalogue API base URL — taken from the `Resource Catalogue` capability endpoint in `endpoint_report.json` with `/api/service/all` appended |
| `quantity`      | No       | `10`                                | Maximum number of services to retrieve |
| `dashboard_dir` | No       | `../dashboard/data`                 | Output root directory |

Triggered via: `POST /api/run/catalogue-services` with body `{ "node": "...", "catalogueUrl": "..." }` — no credentials required.

### CheckServiceUptime (Service Monitoring)

Builds `argo_uptime_report.json` via a source abstraction, tried in order:
the ARGO capability-monitoring metrics API (default, public — no API key
needed), the public ARGO dashboard scrape (fallback), then the legacy ARGO
API (fallback, requires an API key). See
[Check Service Uptime](CHECK_SERVICE_UPTIME.md) for the ARGO tenant-name
resolution rules both of the first two sources use.

```text
CheckServiceUptime NODE_NAME [API_KEY] [START_DATE] [END_DATE] [dashboard_dir]
```

| Argument        | Required | Default          | Description |
| --------------- | -------- | ---------------- | ----------- |
| `NODE_NAME`     | Yes      | —                | Node name; must match `node_registry_summary.json` |
| `API_KEY`       | No       | —                | Legacy ARGO API key, only used if both of the above sources are unavailable; falls back to `check.api-key-argo` from config; may be left blank entirely |
| `START_DATE`    | No       | 1 month ago      | `YYYY-MM-DD` |
| `END_DATE`      | No       | Today            | `YYYY-MM-DD` |
| `dashboard_dir` | No       | `../dashboard/data` | Output root directory |

Triggered via: `POST /api/run/service-uptime` with optional body `{ "node": "...", "apiKey": "..." }` — no credentials required in the normal case; `apiKey` is only used by the legacy fallback.

### CheckOtherMetrics (Federated Search)

Resolves the Proposed Validation Metrics document's cross-node visibility
metrics (4, 5, 6, 9, 10, and 11) and writes `front_office_metrics_report.json`.
Needs no direct input beyond the node name — every PID and Front Office
endpoint it needs, including the Sandbox's, is resolved from
`node_registry_summary.json` and each node's `endpoint_report.json`, so
`CheckNodeCapabilities` should be run first (or already be up to date).

```text
CheckOtherMetrics NODE_NAME [dashboard_dir]
```

Triggered via: `POST /api/run/other-metrics` with body `{ "node": "..." }` — no credentials required.

### CheckAll (Check All)

Runs `CheckNodeCapabilities` once for the whole Node Registry, then — for
every node it just wrote a summary for — Exchange Services, Service
Monitoring, and Federated Search, one node at a time. A failure checking one
node (or one of its three checks) doesn't stop the run; the job's final
message reports how many nodes were checked and an ok/skipped/failed count
per check type.

Triggered via: `POST /api/run/check-all` — no body required, same
`check.api-key-node` requirement as `CheckNodeCapabilities`. Can also be run
on a schedule instead of (or as well as) by hand — see **Scheduled Check
All** under Configuration below.

## Adding a New Node

When a new node has been added to the [EOSC Node Registry](https://node-devel.eosc.grnet.gr/federation/eosc-beyond/home),
run `CheckNodeCapabilities`. This updates `node_registry_summary.json` and
creates `data/NEW_NODE_NAME/endpoint_report.json`. The new node will then
appear on the dashboard automatically.

To populate the remaining reports, run `CheckCatalogueServices`,
`CheckServiceUptime`, and `CheckOtherMetrics` against `NEW_NODE_NAME` (or run
**Check All**, which does exactly this for every node). The generated files
are placed in `data/NEW_NODE_NAME/`.

Missing reports are handled gracefully throughout the UI:

- The landing page shows "No report" rows and greyed-out chips on the node
    card.
- The node detail page shows "Not available" panels for each missing report,
    rather than errors.
- If all four reports are absent for a node, the detail page shows:
    _"No report files found for NODE"_.

## MVP Requirement

A node is considered to meet the **Minimum Viable Product (MVP)** requirement
if its `endpoint_report.json` contains both of the following capabilities with
`status: "Available"`:

- `AAI`
- `Resource Catalogue`

The MVP status is shown:

- On the **landing page** — as an `X/Y Meet MVP` tile in the summary strip,
    and as a row on each node card.
- On the **node detail page** — as a ✓ or ✗ card in the overview strip.

## Running Locally

The dashboard requires a running Spring Boot backend for the `/api/` routes.
For static file development only (no run-checks functionality), any HTTP server will do.

```bash
# Spring Boot (full functionality)
mvn spring-boot:run
# or
java -jar target/pilot-node-dashboard-1.0.0-SNAPSHOT.jar

# Static file server (read-only, no checks)
python3 -m http.server 8080
# or
npx serve .
```

Then open `http://localhost:8080/index.html`.

## Configuration

Set the following properties in `application.properties`:

| Property              | Description |
| --------------------- | ----------- |
| `dashboard.data-dir`  | Path to the data directory (e.g. `../dashboard/data`) |
| `check.node-name`     | Default node name for `CheckNodeCapabilities` |
| `check.api-key-node`  | API key for `CheckNodeCapabilities` (also required for **Check All**) |
| `check.api-key-argo`  | Fallback ARGO API key for `CheckServiceUptime`'s legacy-API source only; the default capability-metrics API and dashboard-scrape sources are public and need no key |

### Scheduled Check All

**Check All** can also run automatically on a cron schedule instead of (or as
well as) being triggered from the UI:

| Property                              | Default            | Description |
| -------------------------------------- | ------------------ | ----------- |
| `check.check-all.scheduled.enabled`    | `false`             | Set to `true` to turn the scheduled run on |
| `check.check-all.scheduled.cron`       | `0 0 3 * * *` (daily at 03:00) | Spring 6-field cron expression (second minute hour day-of-month month day-of-week) |

`application.properties` is not hot-reloaded, so a restart is needed after
changing either value. A scheduled run goes through the same `CheckAll` job
as the **Check All** button, so it shows up alongside manually-triggered jobs
at `GET /api/run/status`.

## Navigation

### Landing page — `index.html`

Shows all registered nodes in a card grid. Each card displays:

- Overall health badge (Healthy / Degraded / Down / No data)
- Endpoint availability (available / total, with percentage)
- Exchange Services (active / total)
- ARGO uptime percentage
- Compliance tier
- Federated Search metrics visibility (visible / total)
- Report availability chips (present = blue, missing = grey)

The summary strip at the top shows aggregate totals across all nodes: total
nodes, healthy nodes, degraded or missing, capability uptime percentage,
available capabilities, Federated Search metrics visibility, and nodes
meeting each compliance tier.

Click any node card to open its detail page.

The **Run checks** menu (top right) triggers data collection for the whole
network:

- **Check All** — runs Node Capabilities, then Exchange Services, Service
    Monitoring, and Federated Search for every registered node, one node at a
    time. No credentials required beyond `check.api-key-node`. This can take
    much longer than a single check, so the UI polls for up to 30 minutes
    before giving up (see Configuration above for running it on a schedule
    instead).
- **Node Capabilities** — runs `CheckNodeCapabilities` against every
    registered node and refreshes `endpoint_report.json` for each, on its own.

### Node detail page — `node.html#NODENAME`

The node name is carried in the URL hash fragment (e.g. `node.html#CESSDA`),
which means navigation works correctly with server-side URL rewriting and the page can be bookmarked or shared directly.

The page shows:

- **Overview strip** — endpoints available, active Exchange Services, average
    ARGO uptime, and compliance tier at a glance.
- **Core Services Integration Report** — one card per capability with type,
    URL, HTTP status, and version, grouped by compliance tier.
- **Exchange Services Report** — table of services with name, abbreviation,
    URL, and availability status.
- **ARGO Uptime Report** — one card per monitored service, each showing
    Availability, Reliability, and Uptime percentages plus how many months
    (or days, for the dashboard-scrape and legacy sources) were monitored,
    and the reporting period.
- **Federated Search** — one card per metric (4, 5, 6, 9, 10, 11) evidencing
    cross-node visibility, per the Proposed Validation Metrics document.

Use the **Switch node** dropdown (top right) to move directly to another node's
detail page without returning to the landing page.

The **Run checks** menu (top right) triggers node-specific data collection —
none of the three needs any credentials:

- **Exchange Services** — runs immediately using the node's Resource
    Catalogue endpoint, read from `endpoint_report.json`.
- **Service Monitoring** — runs immediately against the public ARGO
    capability-metrics API (or its fallbacks); no API key prompt any more,
    since the default source needs none.
- **Federated Search** — runs immediately; resolves every PID and Front
    Office endpoint it needs, including the Sandbox's, from data already
    collected by Node Capabilities.

The breadcrumb at the top of the page returns to the landing page.
